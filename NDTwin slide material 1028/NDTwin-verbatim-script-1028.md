## P01 〈P4 support since 10/14〉

（指著標題）

老師好，今天報告 NDTwin 的 P4 支援在 10/14 之後又多了什麼。10/14 那次我報告過幾種新的表項比對寫法、交換機拒絕寫入時看得到的原因、外部控制器底下的斷線偵測，還有一套檢查 P4 功能的工具；那些今天不重講，只講之後新增的部分，修 bug 的東西也不放。這五項都在一台全新的實驗室 VM 上、用一般版 bmv2 真的跑過，只驗功能，沒有效能或時間的數字。

## P02 〈New P4 capabilities since 10/14〉

（指著表格，先指最右邊 verified 那一欄，再從第一列往下）

這五列就是五個新功能，最右邊這一欄是怎麼驗的。先講兩個詞：P4 是一種可以自己定義交換機怎麼處理封包的程式語言；bmv2 是 P4 官方的軟體交換機，跑在一般電腦上。

第一、二列是讀取。register 就是 P4 程式自己在交換機裡存的變數；direct counter 是掛在某張表上、每一筆規則各有一個的計數器，可以看每一筆被打到幾次。現在開發者可以透過 P4 proxy，也就是 NDTwin 裡專門跟 bmv2 溝通的那一層，直接讀這兩樣東西。這兩個已經在實驗室的 VM 上實際跑過，一樣只驗功能，沒有效能數字。

第三列是 CIDR 網段，就是像 /24 這樣一次指一整段位址。以前 P4 上只能寫單一主機，現在透過 Ryu 相容 API，也就是 OVS 那邊原本在用的那套寫規則介面，可以直接下一個 /24。第四列是規則遺失通知，後面兩頁會細講。這兩列也都在實驗室的 VM 上跑過。

第五列是轉換工具，兩篇論文的 P4 app，int-v1 和 ONTAS，現在可以轉成 NDTwin 的套件。轉出來的套件已經在實驗室的 NDTwin 網路上實際跑起來。

## P03 〈Rules wiped by a push: report, not replay〉

（指著表格的兩欄：左邊 replay automatically，右邊 report; the app resends）

接下來這頁是這一輪最主要的設計取捨。先解釋一下 pipeline 重推：就是把 P4 程式重新載進交換機，載的那一下，交換機上的表會全部清空。proxy 重啟，或某台交換機重啟後被重新接管，都會發生這件事。

問題是：app 經由 Ryu 相容 API 下的規則，被清掉之後，要不要由系統自動裝回去？左邊是自動重放，右邊是只回報、讓 app 自己重送。自動重放聽起來比較方便，可是 proxy 只記得當初收到什麼請求，不記得為什麼要裝。舉個例子，流量工程的 app 為了避開壅塞裝了一條繞路，後來壅塞早就沒了，自動重放就會把這條已經沒有理由的繞路又裝回來。

所以我們選右邊：proxy 把哪些規則不見了說清楚，由真正知道理由的 app 決定要不要重送。代價也要講：app 重送之前，這些規則就是不在交換機上。控制面自己的基本路由，重推的時候本來就會重新裝回，不在這個問題裡。

## P04 〈How the rule-loss notice reaches the app〉

（指著圖，從左下第 1 步沿箭頭一路指到右上第 5 步，最後指右下虛線的第 6 步）

剛剛講的回報，這張圖是它怎麼一路傳到 app。四條橫帶由上到下是 app、NDTwin 的 kernel、P4 proxy、bmv2 交換機。

第 1 步 pipeline 重推，第 2 步交換機上的表全部清空。第 3 步，proxy 推完之後對照自己的紀錄，把經由 Ryu 路徑裝、這次被清掉的規則逐筆整理出來，每台交換機分開記。第 4 步，kernel 本來就每秒問 proxy 一次狀態，就順便把這份紀錄原封不動複製到 kernel 拓樸圖上那台交換機的節點；kernel 拓樸圖就是 NDTwin 核心維護、app 透過 API 讀的那張網路圖。同時 kernel 也會在 log 記一行錯誤。

第 5 步，設計上是 app 看到新紀錄就重送自己的規則，每筆紀錄有自己的編號，同一筆只處理一次。但要老實說，目前還沒有任何 app 接上這個通知，所以第 5 步和第 6 步畫成虛線：規則要等 app 重送才會回來，系統不會自己裝。

## P05 〈Reading registers and direct counters〉

（先指上面的 App，再指左邊 P4Runtime 那條線，最後指右邊兩個檢查框和紅色的 503、502）

接下來看這兩個怎麼讀。兩個讀取都在 P4 proxy 的 API 上，app 直接呼叫。

左邊是 direct counter，走 P4Runtime，也就是控制器跟 P4 交換機講話的標準協定。一次讀回整張表，每一筆帶自己的比對條件和 bytes、packets。讀失敗會回 503，而且明說這不是 0、也不是空表。

右邊是 register。bmv2 的 P4Runtime 不支援讀 register，所以只能繞到 bmv2 自己的 Thrift 服務。繞過去的風險是，那個 port 上回答的不一定是我們以為的那台交換機。所以每一次讀之前做兩個檢查：先確認這台交換機有回應 P4Runtime，再在同一條 Thrift 連線上確認它回報的裝置編號和 port 跟這台交換機一樣，任何一個不過就回錯誤，什麼都不讀。

限制先講清楚：這條路只有 bmv2 有，硬體交換機沒有；register 最寬 63 bit；如果原本那台交換機還在回應 P4Runtime，同時有一台裝置編號和 port 都一樣的冒牌交換機佔住那個 Thrift port，這兩個檢查擋不住。

## P06 〈Verified live on a fresh lab VM〉

（先指前兩列 CIDR，再指後三列規則遺失通知，最後指「re-adopt: other 9 switches」那列）

這頁是實驗室實測的結果。我們開了一台全新的實驗室 VM，用一般版的 bmv2，10 台交換機、4 台主機。先講清楚兩件事：第一，這只驗功能，沒有任何效能或時間的數字；第二，這些結果是先在 VM 裡繞過下一頁那兩個問題之後才跑出來的。

前兩列是 CIDR。一筆 /24 寫進去，從交換機讀回來確實就是一筆 /24；對照組是控制面原本那筆單一主機的路由，讀回來是 /32，所以讀得出兩者的差別。另外經由 kernel 的 flow API 下一筆 /25，交換機也接受了，條目多了一筆。

後三列是規則遺失通知，兩種觸發都測了：一種是交換機行程真的重啟、再重新接管，另一種是 proxy 重啟。兩種都正確列出剛裝的 2 條規則，kernel 拓樸圖上的那份和 proxy 的一模一樣，交換機上那 2 條也確實不見了。其他 9 台交換機的紀錄都沒有被動到，這是重新接管那一段的對照。

最後補一句：這裡驗的是寫得進去、讀得回來、通知正確，實驗室裡沒有送封包看 /24 怎麼轉；送封包的測試是在臨時 bmv2 上離線做的。

## P07 〈What a fresh machine exposed〉

（指著表格三列，最後指右邊 next step 那一欄）

接下來這頁，是在一台全新的機器上把 NDTwin 裝起來時碰到的三個問題。這三個都還沒修好，所以不算新功能，我照實列出來。

第一個，P4 網路啟動時，會固定到某一個使用者的家目錄去找流量產生器，實驗室小幫手的設定檔也沒有可以改這個路徑的欄位。我們在 VM 上的那個使用者身上看到網路起不來，10 台交換機一台都沒有。換成其他使用者應該也一樣，不過這是從寫死的路徑推出來的，實際只看到一個使用者。

第二個，全新的 checkout 第一次啟動時，log 目錄是由以 root 執行的拓樸程式建立的，P4 proxy 用一般使用者的身分寫不進自己的 log，整個啟動就失敗。這兩個正在修，會附測試。

第三個是文件問題。readopt 就是交換機重啟之後，proxy 重新接管它。它的前提是那台交換機的行程真的重啟過；對一台還在跑的交換機下這個指令，會被拒絕，回覆說交換機沒被動到。API 文件沒寫這個前提，要補上。

## P08 〈Limits of the new features〉

（指著表格，一列一列往下，每一列都指一下右邊的 next step）

這頁是新功能本身還不夠的地方。

第一列，這兩個讀取 API 目前只寫在程式碼的說明裡，使用者文件還沒有，剛剛講的 63 bit 和冒牌交換機這兩個限制也還沒寫出來，要一起補進文件。

第二列最容易誤會。P4 上比的是前綴長度，不是 OVS 那種優先權；一般的網路裡每台交換機對每台主機都有一筆 /32，所以想用一筆 /24 改某台主機的走法，在那台交換機上不會生效，只對沒有 /32 的位址有用。這點要寫進文件。

第三、四列各有一件事要決定，目前只是提案、還沒決定。一個是有幾種網段寫法，kernel 會先回 200 排進佇列，到 P4 proxy 才被拒絕，提案是讓 kernel 事先擋掉；另一個是如果 bmv2 先重啟、接著 proxy 也重啟，而 kernel 和 app 一直在跑，那份遺失紀錄會說 0，但規則其實已經不見了，提案是在 proxy 啟動時把這種情況標出來。

最後一列，遺失通知做好了，但還沒有 app 收到通知就重送，需要一個真的這樣做的 app。

## P09 〈What comes next〉

（先指左邊 NOW 那一欄，再指右邊 NEXT 那一欄）

最後是接下來的安排。圖上不寫日期，順序就是左右這兩欄；每一個框都對應到第 7 頁或第 8 頁某一列的下一步，所以前面講的弱點都有對應的後續。

左邊 NOW 是先補的：新機器上那兩個問題，修好並附測試；文件補三件事，重新接管的前提、兩個讀取 API 和它們的限制，還有 P4 上 /24 和主機 /32 的關係。

右邊 NEXT 是再來要做的：剛剛那兩個提案要先做決定；再做一個真的會依遺失通知重送規則的 app。這兩個決定，一個是讓 kernel 事先擋掉 P4 會拒絕的網段寫法，一個是在 proxy 啟動時標出那種說 0 的情況，目前都還只是提案。

## 被問到時可以這樣答

- **為什麼選回報，不直接幫 app 重放？** proxy 的紀錄只有當時收到的請求，沒有當時的理由，自動重放可能把一條理由已經不在的繞路裝回來。真正知道理由的是 app，所以由它決定要不要重送；代價是 app 重送之前規則不在。
- **這次有量效能嗎？** 沒有。實驗室這一輪只驗功能，有沒有寫進去、讀不讀得回來、通知對不對，沒有時間、效能或速率的數字。
- **/24 真的會轉封包嗎？** 實驗室裡只驗了寫進去和讀回來，沒有送封包。送封包是在臨時 bmv2 上離線測的，/32、/24、/16 三層照最長前綴轉，兩種 bmv2 各 11 項都通過；但要記得，交換機上有某台主機的 /32 時，/24 對那台主機不生效。
- **為什麼要先繞過問題才跑得起來？** 因為全新機器上碰到第 7 頁那兩個問題：流量產生器的路徑寫死，還有 log 目錄被 root 建走。VM 裡先繞過去才跑實測，這兩個正在修、會附測試。
- **換成真的硬體交換機呢？** 讀 register 走的是 bmv2 自己的 Thrift 服務，硬體目標沒有這個服務，那條 API 會直接回 503。這一輪所有結果都是在 bmv2 上，沒有在硬體 P4 交換機上跑過。
- **register 那些在實驗室上跑過了嗎？** 已經在實驗室的 VM 上跑過，只驗功能、沒有效能數字。
- **實驗室上 register 和 direct counter 到底比了什麼？** register 從 API 讀到的值，和交換機自己的命令列工具讀到的一模一樣，4 台交換機、兩個 register 都比過，只讀一格也比過；direct counter 則是 ping 10 次以後，路徑上每一筆剛好多 10 個封包。對照組也都對：名字不存在回 404、索引超出範圍回 400、交換機停掉回 503 而且不帶任何值。要老實補一句，其中一個 register 全程都是 0，所以真正有數值的比對是另一個。
- **app 已經會依通知自動重送了嗎？** 還沒有，目前沒有任何 app 接上這個通知；通知本身已經在實驗室驗過，接上的 app 是下一步。
- **遺失紀錄存在哪裡？** 只存在 proxy 的記憶體裡；如果 proxy 在 kernel 讀到之前又重啟一次，那一份就看不到了。

## 不要這樣說

- ❌「register、direct counter 在任何 P4 交換機上都能讀」。✅「已在實驗室的 VM 上驗過功能，一般版 bmv2，沒有效能數字。」
- ❌「兩篇論文的 app 在 NDTwin 上跑得跟原本一樣快」。✅「已在實驗室的 VM 上驗過功能，一般版 bmv2，沒有效能數字。」
- ❌「規則被清掉之後系統會自己補回來」。✅「經由 Ryu 路徑下的規則只會回報，要 app 自己重送；目前還沒有 app 接上。」
- ❌「通知半秒內就到 kernel」或任何時間數字。✅「這一輪只驗功能，沒有量時間。」
- ❌「用 /24 就能改任何主機的走法」。✅「在 P4 上比的是前綴長度，交換機有那台主機的 /32 時，/24 對它不生效。」
- ❌「那兩件事我們已經決定這樣修」。✅「kernel 事先擋網段寫法、proxy 啟動時標出說 0 的情況，這兩個目前只是提案，還沒決定。」
