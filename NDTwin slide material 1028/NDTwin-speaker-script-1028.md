## P01 P4 support since 10/14（開場）

今天報告 10/14 之後，NDTwin 的 P4 支援多了哪些功能。
修 bug 的部分今天不放，只講開發者現在多了什麼可以用。
這五項都在一台全新的實驗室 VM 上、用一般版 bmv2 真的跑過，只驗功能，沒有效能或時間數字。
最後兩頁會講還不夠的地方，跟接下來要做什麼。

## P02 New P4 capabilities since 10/14（五個新功能）

這一頁是五個新功能，最右邊一欄是驗證方式：五個都在實驗室的 VM 上實際跑過，只驗功能。
前兩個是讀取：開發者可以直接讀自己 P4 程式裡的 register，也可以讀某一張表的 direct counter，看每一筆規則被打到幾次。
第三個是在 P4 上可以下一整個網段，例如 /24，以前只能下單一台主機；第四個是規則遺失通知，表被清空的時候，app 可以從拓樸圖上看到哪些規則不見了。
第五個是轉換工具變強了，兩篇論文的 P4 app，int-v1 和 ONTAS，現在可以轉成 NDTwin 的套件，也已經在實驗室 VM 的 NDTwin 網路上起起來跑過，兩個都通過。

## P03 Rules wiped by a push: report, not replay（設計決定）

這一輪最主要的設計取捨，是 pipeline 重推之後，app 經由 Ryu 相容路徑下、被清掉的規則，要不要自動裝回去。
自動裝回去看起來比較方便，可是 proxy 只記得當初收到什麼請求，不記得為什麼要裝。
舉例來說，流量工程的 app 為了避開壅塞裝了一條繞路，壅塞已經沒了，自動裝回去就會把一條沒有理由的繞路裝回來。
所以我們選擇只回報、不重放，由真正知道理由的 app 自己決定要不要重送；代價是 app 重送之前，那些規則就是不在。

## P04 How the rule-loss notice reaches the app（通知怎麼傳到 app）

觸發有兩種：P4 proxy 重啟，或是某台交換機重啟後被重新接管，兩種都會把表清空。
proxy 推完 pipeline 之後，把經由 Ryu 路徑裝、這次被清掉的規則逐筆列出來；kernel 本來就每秒問 proxy 一次，就順便把這份清單複製到拓樸圖上那台交換機的節點。
設計上是由 app 看到新的清單就重送自己的規則，但目前還沒有任何 app 接上這個通知。
所以第 5 步和第 6 步畫成虛線：規則要等 app 重送才會回來，系統不會自己裝。

## P05 Reading registers and direct counters（讀取的路徑）

這兩個讀取都在 P4 proxy 的 API 上。
direct counter 走 P4Runtime，一次把整張表每一筆的計數讀回來。
register 比較麻煩：bmv2 的 P4Runtime 根本不支援讀 register，所以只能繞到 bmv2 自己的 Thrift 服務。
繞過去的風險是那個 port 上回答的可能不是我們以為的那台交換機，所以每次讀之前都先確認交換機還活著、而且 Thrift 那一端回報的裝置編號和 port 跟這台交換機一樣，有一個不對就不讀，直接回錯誤。

## P06 Verified live on a fresh lab VM（實驗室實測）

這一頁是在一台全新的實驗室 VM 上跑的，一般版 bmv2，10 台交換機、4 台主機，只驗功能，沒有效能數字；而且是先在 VM 裡繞過下一頁的兩個問題之後才跑的。
網段的部分：/24 寫進去，從交換機讀回來確實是一筆 /24；經由 kernel 的 flow API 下一筆 /25，交換機也接受了。
遺失通知的部分，兩種觸發都做了：剛裝的 2 條規則都被正確列出來，kernel 拓樸圖上的那份和 proxy 的一模一樣，交換機上那 2 條也確實不見了；其他 9 台交換機的紀錄都沒有被動到（這是重新接管那一段的對照）。

## P07 What a fresh machine exposed（全新機器暴露的問題）

在一台全新的機器上把 NDTwin 裝起來，碰到三個還沒修好的問題，我照實列出來。
第一，P4 啟動時固定到某一個使用者的家目錄找流量產生器；我們在一個使用者身上看到網路起不來，10 台交換機一台都沒有，換成其他使用者也會一樣，這是從寫死的路徑推出來的。
第二，全新的 checkout 第一次啟動時，log 目錄被以 root 執行的拓樸程式建走，proxy 寫不進自己的 log，整個啟動失敗。
第三，重新接管交換機的前提是那台真的重啟過，對還在跑的交換機下指令會被拒絕、回覆說交換機沒被動到，但文件沒寫這個前提；前兩個正在修、會附測試，第三個是補文件。

## P08 Limits of the new features（新功能的限制）

這頁是新功能本身還不夠的地方：第一，兩個讀取的 API 和它們的限制還沒寫進使用者文件。
最容易誤會的是網段：P4 比的是前綴長度，不是優先權，一般網路裡每台交換機對每台主機都有一筆 /32，所以想用 /24 改某台主機的走法，在那台交換機上不會生效。
另外有兩件要決定怎麼處理：有幾種網段寫法會先回 200、之後才被 P4 拒絕；還有如果 bmv2 先重啟、接著 proxy 也重啟，而 kernel 和 app 一直在跑，那份遺失紀錄會說 0。
最後，遺失通知做好了，但還沒有任何 app 收到通知就重送規則。

## P09 What comes next（接下來）

接下來先補的是新機器上那兩個問題，以及三份文件：重新接管的前提、兩個讀取 API 和它們的限制，還有 /24 跟主機 /32 的關係。
再來要決定那兩件事，並做一個真的會依遺失通知重送規則的 app。

## 被問到時不要這樣說

- ❌「register 讀取在任何 P4 交換機上都驗證過了」。✅ 在實驗室 VM 上、一般版 bmv2 驗過功能，比對的是讀到的數值；只有 bmv2，沒有量效能。
- ❌「兩篇論文的 app 在 NDTwin 上跑得跟原本一樣快」。✅ 轉出來的套件在實驗室 VM 的 NDTwin 網路上功能檢查都通過；這一輪沒有量效能。
- ❌「proxy 重啟之後，app 經由 Ryu 路徑下的規則會自己回來」。✅ 不會，這些設計上只回報；要 app 自己重送。
- ❌「app 已經會依遺失通知自動重送」。✅ 還沒有任何 app 接上這個通知。
- ❌「/24 可以拿來改任何主機的走法」。✅ 在 P4 上，交換機有那台主機的 /32 時，/24 對它不生效。
- ❌「實驗室的結果顯示 /24 的封包轉發是對的」。✅ 實驗室只驗了寫進去、讀回來；封包實際怎麼轉，是在臨時 bmv2 上離線送封包驗的。
- ❌「通知半秒內就到 kernel」或任何時間、效能、速率數字。✅ 這一輪的實驗室結果只有功能，沒有量時間。
- ❌「NDTwin 可以讀任何 P4 目標的 register」。✅ 只有 bmv2，因為走的是 bmv2 自己的 Thrift 服務；硬體目標沒有這條路。
- 被問到跟 10/14 的關係：第 7 頁第一個問題，是 10/14 排第一名的「綁在一台機器上」那一類，第一次在實機上看到；第 3 頁的決定，取代了 10/14 路線圖裡原本要把路由請求重放回去的那一部分。
- 被問到實驗室上 register 和 direct counter 比了什麼：register 從 API 讀到的值，和交換機自己的命令列工具讀到的一樣，4 台交換機、兩個 register 都比過，單一格也比過；ping 10 次，路徑上每一筆 direct counter 剛好多 10 個封包、980 bytes。對照組也都對：名字不存在回 404、索引超出範圍回 400、交換機停掉回 503 而且不帶任何值。要補一句：其中一個 register（last_time_reg）全程都是 0，所以真正有數值的比對是另一個 byte_cnt_reg。
- 被問到遺失紀錄存在哪裡：只在 proxy 的記憶體裡；如果 proxy 在 kernel 讀到之前又重啟一次，那一份就看不到了。
- 被問到心跳偵測：那是 10/14 之前就有的功能，這次只是在新機器上重跑一次、通過，不算新結果。
