## 1. Why a table, not a chart (unchanged from 09-04, and it still holds)

Every value here is a **status code / outcome string** — "200 installed,"
"502 absent," "present (type SELECT)," "404 no_such_group." There is no length,
height or position that would represent these honestly as bars; coding outcomes
as 0/1 would manufacture an axis that does not exist in the data and invite a
reader to compare magnitudes that are not there. The dataviz form guide puts
categorical outcomes that all carry meaning in a table, and the before/after
requirement does not change that — it just makes it two tables with identical
columns and identical column widths, so the eye compares straight down a column.

## 2. Why both `813` and `899` stay (orchestrator's ruling, and the evidence for it)

They are not the same control and they do not prove the same thing:

- **`899`** — a group id that was **never installed**. Run through
  `modify_group_entry` (and, on 09-04, `delete_group_entry`). It proves the
  **delete/modify** branch reads the switch back: asked about something that
  genuinely is not there, it says `no_such_group` rather than inventing a
  success. This was the 09-04 carrier.
- **`813`** — a `SELECT` group with all-zero bucket weights that **OVS really does
  accept**. It proves the **install** branch reads the switch back *and still
  answers 200 when the switch did take it*: `install → 200 "installed"`,
  `groupdesc → present (type SELECT)`, `delete → 200 "deleted"`. Without this
  row, the after side would only show the fix turning 200s into 502s, and a
  reader could not rule out "they just made install always fail."

`813` is the row that gives the after side its discriminating power, so dropping
it would be the expensive deletion, not the cheap one.

### 2a. 🔴 `813` is **not** new data — correction to `figs-after.json`

`figs-after.json`'s `_row4_note` says 「第 3 列（813）是今晚新的」. That is true of the
*figure* and false of the *data*. 09-04's raw `logs/r2-41-b1-group-extra.log`
already contains `813` with the identical three cells:

```
-- install_group_entry 813 type=SELECT with all-zero weights (OVS rejects weight 0 on SELECT):
{"outcome":"installed","status":"Group entry installed"} HTTP=200
-- groups on s4 now:
[{"buckets": [{"weight": 0, ... "actions": ["OUTPUT:1"]}], "group_id": 813, "type": "SELECT"}]
-- cleanup
  delete 813 HTTP=200
```

It was measured on 09-04 and simply not tabled. **This matters:** a control that
is all-green and appears only on the after side has zero discriminating power —
it cannot distinguish "the fix works" from "the control was always going to be
green." Because `813` was green on the broken binary too, its green on the fixed
binary is evidence that the fix did **not** break the accept path, which is
exactly the claim it is being asked to carry.

It is nevertheless shown **only in the after block**, per the orchestrator's
"before 用 09-04 的 2 列" instruction. If Adam wants the before block to carry it
as well (3 rows before / 4 after), the row is one line in `before_rows` at
`make_overnight_figs.py:260-267` and the raw above is the citation.

## 4. Cell text: what was abbreviated, and where the verbatim lives

The figure abbreviates two long strings to keep the cells legible. Neither
changes a value:

  `"group 4294967295 on dpid 4 is not on the switch after the install was
  forwarded and acknowledged; the switch did NOT take it"`. The cell shows
  `502 {"outcome":"absent"}` plus the quoted tail `"the switch did NOT take it"`.
  Quotation marks mark it as an excerpt.
- **the `813` groupdesc object.** Raw carries the whole bucket list; the cell
  shows `present (type SELECT)`.

**Before-side cells were re-rendered into the after side's format** so the two
blocks are column-comparable: 09-04's figure printed `200 "installed"` and
`404 "no_such_group"`, this one prints `200 {"outcome": "installed"}` and
`404 {"outcome": "no_such_group"}`. The status codes and outcome strings are
identical and verbatim from `logs/r2-41-b1-group-extra.log`; only the typography
changed.

`899`'s two `— not attempted` cells are literal: R0 ran `modify_group_entry` on
`899` but **not** `install_group_entry` and **not** `delete_group_entry`. 09-04
did run `delete_group_entry 899` (→ 404, `logs/r2-40-b1-group.log`); this round
did not repeat it. The figure says "not attempted" rather than reusing 09-04's
answer in an after-side row.

## 5. The tint, and a second correction to `figs-after.json`

Tint is a **status wash behind full text**, never colour alone — every cell
prints its own status code and outcome string, so a reader who cannot see the
wash loses nothing. Contrast of `INK_PRIMARY` on each wash was measured, not
eyeballed: critical wash 16.2:1, good wash 17.1:1, neutral 19.7:1, header
16.8:1 (WCAG AA needs ≥ 4.5:1 for body text; all four clear it by >3×). The dataviz skill's
`validate_palette.js` was **not** run — `node` is not installed on this laptop —
but it validates categorical series separation, which is not the job this
colour is doing here; the contrast numbers above are the check that applies.

- **after side** — R0's rule, "three channels agree = good": on all four rows
  `install`, `groupdesc` and `delete` now give the same answer, so there is no
  critical wash anywhere. `899`'s `delete` cell is **neutral, not green**,
  because it was not run this round — an unmeasured cell must not be painted as
  a passing one.
- **before side** — kept exactly as 09-04 published it: `[0, 1, 1, 2]`.
  install (200 "installed") and groupdesc (absent) contradict each other and are
  washed critical; delete (404 no_such_group) told the truth and is washed good.

🔴 **`figs-after.json`'s `_tint_note` misquotes this**, saying 09-04's rows 1–2
were `[0,1,1,1]`. The published `fig4()` had `[0,1,1,2]`. The `2` matters: it is
the whole point of the 09-04 finding — *one* branch of `guardedMod` read the
switch back and the other did not, so the delete cell was never the broken one.
Re-tinting it to `1` retroactively would erase the asymmetry the before side
exists to show. **The published tint was kept.**

## 7. Caveats (carried forward from 09-04, still true)

- **2/2 is both reserved ids tried, not a large-N sample.** The mechanism —
  only one branch of `guardedMod` called back to the switch — was read directly
  in R2's own account of B1's earlier fix (`rounds/03` §3-4: "the fix for #1 was
  installed only on delete, never generalised to the sibling branch"), so this
  is a confirmed code-shape claim, not a coincidence across two samples. The
  after side has the same shape: 2 reserved ids + 2 controls, on one binary.
- **`OUTPUT:999`** (an out-of-range but non-reserved port number) is **not** a
  reserved value and is accepted normally by OVS — it does not expose the gap
  and is not a usable carrier for a repro.
- **Switch truth here is Ryu's `groupdesc` REST read**, not `ovs-ofctl`
  (`sudo -n ovs-ofctl` is not in this lab's sudoers). If the claim to prove one
  day is "Ryu itself misreports," this column is not strong enough alone.
- **The 09-04 `812` side-finding is still not in the figure**: a bucket with
  action `NOT_A_REAL_ACTION` came back "installed" with the bucket really
  present but its `actions` shown as `[]` — the requested action was silently
  dropped somewhere in the kernel-or-Ryu path, and that round did not isolate
  which side dropped it. R0 did not re-probe it, so there is no after side for
  it either.
