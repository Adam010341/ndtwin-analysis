## 1. What the three groups are and how each number was read

All three read `GET /ndt/get_flow_dispatch_status` (`counters.succeeded`) before
and after a batch of calls, and independently read Ryu's own
`/stats/flow/4` (switch truth) for the number of rows matching the target
`ipv4_dst`, before and after the same batch. Both deltas are exact — one
`before` and one `after` snapshot bracketing each batch, not a sampled estimate.

| group | calls | succeeded before → after (Δ) | switch rows before → after (Δ) |
|---|---|---|---|
| 20× install, same match (`10.5.4.4`) | 20× `install_flow_entry`, identical `dpid`/`priority`/`match`/`actions` each time | 6 → 26 (**+20**) | 0 → 1 (**+1**) |
| 15× delete, never existed (`10.5.4.99`) | 15× `delete_flow_entry` for a match that was never installed | 26 → 41 (**+15**) | 0 → 0 (**+0**) |
| 1× delete, real entry (control) | 1× `delete_flow_entry` for `10.5.4.4`, which the first group actually put on the switch | 41 → 42 (**+1**) | 1 → 0 (**Δ −1, magnitude 1**) |

The chart plots `succeeded` delta directly, and plots the **magnitude** of the
switch-row change (1 for the two real-change rows, 0 for the phantom-delete row)
so a real addition and a real removal both read as "1 row of real change,"
rather than forcing a sign convention that would make the chart about arithmetic
instead of about the mismatch.

## 2. Why the third group is here

The first two groups on their own could read as "the counter is just broken."
The third (real delete of the entry the first group actually created) is the
**control**: `succeeded` and switch-truth move together (+1 / −1) exactly when
something real happens. `succeeded` is not lying in the sense of being random —
it is counting **"this POST did not error,"** which is a real and defensible
thing to count. The defect is that the API's own 200-body text calls this
"readable afterwards from `GET /ndt/get_flow_dispatch_status`" without
qualifying that "succeeded" means "accepted for programming," not "changed the
network" — a caller who diffs `succeeded` against an expected row count (as a
NSR/TE-style app would) cannot tell the phantom-delete row from the real one
using this endpoint alone.

## 3. Caveats

- This was tested against **duplicate installs of one static rule** and
  **deletes of a rule that was never installed**. It does not by itself say
  anything about `failed` or `dropped_after_stop`, which stayed at 0 throughout —
  those counters were not exercised by this reproduction.
- Switch truth here is Ryu's `/stats/flow/<dpid>` (control-plane read), not
  `ovs-ofctl` (`sudo -n ovs-ofctl` is not in this lab's sudoers — see
  rounds/03 §1). If the thing to prove one day is "Ryu itself misreports," this
  reproduction's switch-truth column is not strong enough on its own.
