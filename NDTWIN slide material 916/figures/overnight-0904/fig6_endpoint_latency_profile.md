# fig6 — API response time by endpoint (OVS4)

Companion to `fig6_endpoint_latency_profile.{pdf,png,svg}` (generated by
`make_overnight_figs.py`, function `fig6()`, 2026-09-04). **Current behaviour
only — this is not a before/after figure; there is no known "fix" pending for
raw HTTP latency.**

**Credibility: 🟢 〔跑過〕**, one sweep. Binary: kernel `cca5e3e4ebc42358`,
helper `6685d3a9`, trunk `f943de8f`. Round: rounds/01-ovs128.md (the sweep step),
raw `logs/ovs128-02b-sweep2.log`, captured 2026-09-04 16:34 by `sweep.py`
(this repo's own smoke-test client, `scratch/overnight-2026-09-04/sweep.py`).
**Every number on the chart is that script's own client-measured wall-clock time
for one HTTP request/response round trip** — it is not southbound (switch-side)
visibility latency, and should not be read as "how long until the switch has
the rule." (Southbound visibility numbers — install ~1.0 s, delete ~6.1 s — are
a separate measurement, noted in rounds/01 and not on this chart.)

**The headline gap:** `install_meter_entry`/`delete_meter_entry` (~1.02–1.03 s)
vs. `install_group_entry`/`modify_group_entry`/`delete_group_entry`
(20–34 ms) — roughly **40×**, for two OpenFlow write families that look the
same shape from the API surface. `modify_meter_entry` (26 ms) is the outlier
inside its own family — install and delete are the slow ones, modify is not,
which points at something specific to meter create/destroy on OVS rather than
"meters are slow" categorically.

## 2. Same sweep, the P4-4 plane (not charted — OVS-only chart by design)

`p4-4-02-sweep.log` (same script, same binary, trunk `f943de8f`, ~17:00) ran the
identical sweep against the P4-4 arm. Flow and power operations are comparable
in order of magnitude:

| endpoint | OVS ms | P4 ms |
|---|---:|---:|
| `install_flow_entry` | 1 | 1 |
| `modify_flow_entry` | 4 | 1 |
| `delete_flow_entry` | 3 | 1 |
| `get_graph_data` | 23 | 11 |
| `set_switches_power_state` (off) | 571 | 247 |
| `set_switches_power_state` (on) | 1485 | 1280 |

`install_group_entry`/`install_meter_entry` and their modify/delete
counterparts are **not** comparable on P4: the P4/bmv2 data plane rejects all
six with `501 {"error":"... not supported on a P4/bmv2 data plane"}`, answered
in ~1 ms each (a fast, correct rejection, not a slow success) — so the
"meter vs. group" story is specific to the OVS plane, which is why this chart
is OVS-only rather than a two-plane comparison.

## 3. Caveats

- One sweep, not a distribution — no repeated-trial error bars exist for these
  numbers. A single 571 ms/1485 ms power-state pair or a single ~1.03 s meter
  pair could include one-off scheduling noise; treat the ~40× meter/group ratio
  as the round's one observation, not a statistically characterized effect.
- `get_path_switch_count` shown here (113 ms, no query params — the full
  12-row matrix) is markedly slower than the single-pair query in the same
  sweep (`?src_ip=&dst_ip=`, 0 ms) — consistent with fig5's finding that this
  endpoint recomputes from the static topology file rather than caching.
