## 1. What is actually plotted, and why it's one dot per row, not two

The 12 dots are `switch_count` from `GET /ndt/get_path_switch_count` for all
12 ordered host pairs (4 hosts × 3 other hosts) on the P4-4 fabric, read from
`p4-4-pathcount-allon.json` (all 40 switch-switch + host edges up). The "after"
marker (small filled dot) is drawn centered exactly on the "before" marker
(larger light ring) because **the two independent perturbations tested this
round produced byte-identical values to the baseline**:

1. **`pathmetric_test.py` (the primary test, 32/40 switch-switch edges failed):**
   declares all 16 undirected switch-switch edges (32 directed) down via
   `POST /ndt/link_failure_detected`, confirms via `get_graph_data` that the
   live topology really did drop to 8/40 edges up, re-reads
   `get_path_switch_count`, and diffs row by row against the pre-declaration
   read. Verbatim output:
   ```
   BEFORE: edges up=40 ; path rows=12
   declared 16 switch-switch edges failed in 0.00s ; codes=[200]
   AFTER : edges up=8 down=32 (0.01s after the declarations)
   path rows now=12 ; rows that CHANGED=0
   VERDICT: every path count unchanged while 32/40 edges read down
   ```
   This is the test the finding is named for, but the script's own output is a
   **verdict** ("rows that CHANGED=0"), not a saved per-row dump — there is no
   JSON file of this specific run's 12 values to plot individually.
2. **The energy app's independent power-off (20/40 switch-switch edges down):**
   `s5`/`s7`/`s9` powered off mid-round (bmv2 processes 10→7,
   `get_graph_data` reporting 20/40 edges up), `get_path_switch_count` read
   again and saved as `p4-4-pathcount-3off.json`. This file **is** itemized,
   and it is character-for-character identical to `p4-4-pathcount-allon.json`
   (both files' 12 `{src_ip,dst_ip,switch_count}` entries match exactly).

Since `get_path_switch_count` is a pure function of the static topology file
(it does not read live link/switch state at all — that is the defect), the
32-edges-down state's per-row values are not a separate unknown: the test's own
row-by-row diff against the same baseline guarantees they equal
`p4-4-pathcount-allon.json` too, even without a saved dump of that specific
run. Plotting one dot per pair, with both perturbations noted in the title,
is therefore an accurate — not an approximated — representation of both runs.

## 2. The pairs (axis labels are IP-suffix shorthand)

Hosts are `10.0.0.1`–`10.0.0.4` (h1–h4 by the fabric's own numbering, not
independently re-verified this round — the chart uses the IP suffixes
directly rather than asserting the h-name mapping). `.1→.2`/`.2→.1`/`.3→.4`/
`.4→.3` (same-leaf pairs) read `switch_count=3`; the other 8 (cross-leaf pairs)
read `switch_count=5`. All 12 are plotted, sorted by value.

## 3. Why this matters

TE polls `get_graph_data` every second to make rerouting decisions; NSR logs
these numbers as "network state." An endpoint whose name and `?src_ip=`
parameter (see P4-2, same round) imply a live routing query, but which is
actually reading a constant baked into the topology file regardless of what
the kernel itself knows is up or down, will hand a false answer to anything
built on top of it — including during exactly the failure scenarios a TE app
exists to react to.

## 4. Caveats

- Only the P4-4 arm tested this (rounds/02). OVS4's equivalent endpoint was not
  independently re-tested this round.
- `?src_ip=` filtering is also broken (P4-2, same round, not on this chart): a
  bogus source IP still returns the full 12-row matrix rather than an error or
  a filtered subset.
