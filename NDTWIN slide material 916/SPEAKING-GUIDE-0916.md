# 第二段　需求來自外部的程式（p3–p6）

## p3　13 支練習題 × 16 個能力維度
**開場**：「先講第一種外部需求。這張是需求清單本身。」

**內容**：直的是 13 支練習題，**橫軸是 16 個能力維度**。每一格是「這支題目需不需要這個能力」，
深色是沒有它就零分、淺色是有用到。做法是逐支讀它的 P4 程式、拓樸檔、控制器腳本，不是看文件寫什麼。
**最底下那一列是我們今天做得到什麼**（綠＝做得到、黃＝部分、灰＝做不到），拿來跟上面對。

**16 個維度分成四群，這樣講比較好記：**

| 群 | 維度 | 是什麼 |
|---|---|---|
| **能不能裝程式**（2） | `pipeline_load` | 載入任意一份編譯好的 P4 程式到指定交換機，**而且同一個網路裡每台可以不一樣** |
| | `tables` | 依表名寫規則，至少支援精確與最長前綴比對，參數依程式宣告的位寬編碼，**而且可以改預設動作** |
| **交換機內建的資源**（6） | `pre_multicast` | 建群播群組，資料面真的複製 |
| | `pre_clone` | 建複製 session，可截斷長度 |
| | `counters` | 讀計數器（封包數與位元組數） |
| | `meters` | 讀寫計量器——**13 支一支都沒用** |
| | `registers` | 讀寫暫存器——13 支只在資料面用，控制面不讀 |
| | `digest` | 收 digest 訊息——**13 支都沒用** |
| **封包長什麼樣**（4） | `packet_io` | 封包上送與下送控制器，含開機時指定 CPU port |
| | `custom_headers` | 非 IPv4 的乙太型別、自訂標頭、標頭堆疊 |
| | `queue_metadata` | 讀佇列深度與排隊時間 |
| | `checksum` | 改過 IPv4 欄位之後校驗和還要算對 |
| **環境與怎麼判對錯**（4） | `ttl_or_hop` | 每跳遞減，**而且收端量得到**——這是唯一分得出封包走哪條路的斷言 |
| | `topology` | 主機與交換機數、埠號對應、**逐連結的頻寬與延遲**、靜態 ARP、預設閘道 |
| | `control_plane_mode` | 三種：開機灌一份 json／跑時有外部控制器／完全沒有（規則寫死在 P4 裡） |
| | `verification` | 判對錯的手段：ping、送收封包比內容、iperf、讀交換機的 log |

**要講的重點**：後面三個「做不到」的格子——計量器、暫存器、digest——**沒有一支題目用到**。
所以我們做不到不代表有缺口。**缺口是「有人要而我們沒有」，不是「我們沒有」。** 這就是這張表存在的理由。

🔴 **要講清楚的口徑**：這一輪**沒有在我們的系統上跑過這 13 支**。9/8 跑過的那四次是在 tutorials 自己的環境跑的，證明的是「題目長什麼樣」，不是「我們跑得動」。**在我們的 fabric 上仍然是 0/13。**

## p4　缺口落在架構的哪一層
**開場**：「對完表之後，把剩下的真缺口放回架構上，看它們住在哪。」

**這張圖想表達三件事：**

**第一，最上面那排是每支練習題自己帶來的東西**——它的 P4 程式、拓樸檔、開機要灌的規則、
有時候還有一支控制器。**那四個箭頭往下指，指到的就是它會撞到我們的哪一個元件。**
這是整張圖的骨架：**外部需求從上面掉下來，我們的缺口就在它落地的地方。**

**第二，缺口全部落在中間那一層，不在最底下的資料面。** 底下是 Mininet 跑的一排 bmv2，
註記寫著「今天只有一份 p4info」。**每支練習題都自帶自己的 P4 程式**，所以暫存器、校驗和、
TTL、自訂剖析器那些能力，**只要「能載入任意程式」成立就自動有了**，我們不必去補自己那支 P4。
⇒ **真缺口全在控制面與觀測面**，也就是中間那兩個框裡。

**第三，徽章上的編號與行數是修法的分佈**，邊框粗細代表第幾階段：

| 缺口 | 落在哪個元件 | 缺什麼 |
|---|---|---|
| G2 ~85 | 拓樸模型 | 只認主機數選檔、主機位置用四等分公式推、交換機寫死十台、**逐連結頻寬完全沒被套用** |
| G4 ~150 | pipeline 載入器 | 只推得動一份寫死路徑的程式，十台同一份，跑時換不了 |
| G5 ~180 | 表寫入器 | 表名、動作名、參數名、位寬全寫死在三張自家表上，**而且沒有任何寫預設動作的路徑** |
| G3 ~15 | election id | 十個 client 共用一個寫死的值（就是右邊那張圖的病灶） |
| G1 ~40 | 封包上送解碼器 | 欄位編號是位置相依的裸常數 ⇒ 換一支程式，遙測靜默歸零 |
| G6 ~30+250 | sFlow 剖析器 | 觀測面只認 IPv4，其他乙太型別整包丟 |

🔴 **這些缺口全部是讀碼推導的，一條都沒在系統上驗證過。**
⚠️ **G2 的徽章畫在 KERNEL 那一欄，但它的程式其實在 proxy**——被問就答 proxy（見 p6）。

## p5　只有跑別人的程式才會暴露的兩件事（兩張圖並排）
**開場**：「這一頁是這一段最重要的。」

**內容**：左邊是**靜默歸零**——我們的遙測鏈路依賴我們自己那支 P4 程式的欄位順序，換一支程式之後每個速率和使用率都變成 0，而且沒有任何錯誤訊息。右邊是**冒名者清空全表**——tutorials 普遍自帶控制器，它跟我們的十個 client 投同一個寫死的選舉編號，所以它可以被接受、清空每一張表、然後回報成功。

🔴 **右邊那條是這一段唯一有實測的**（2026-08-13 量過）；左邊那條是讀碼推導。

🔴🔴 **兩句不能講錯的**（09-16 查證）：

1. **不是「每支都自帶控制器」。** 13 支裡**只有 2 支**（`flowcache`、`p4runtime`）自帶跑時控制器；
   10 支是開機灌一份 json，1 支（`calc`）連控制面都沒有。
   正本 `GAP-ANALYSIS.md` §1 寫「tutorials 普遍自帶 `mycontroller.py`」——**那句誇大了，不要照唸。**
2. **不是「搶通道」，是身分撞號。** 這不是頻寬或連線在搶。P4Runtime 的規則是：
   一台交換機同時只有一個 primary 可以寫，誰是 primary 由 `election_id` 決定，
   而**規格明訂 server 要用請求訊息裡帶的那組三元組認人，不是用它從哪條連線進來認人**。
   我們十個 client 都用**寫死的 `(0,1)`**；外面的控制器也用 `(0,1)` ⇒ 在交換機眼裡**它就是 primary**。

🔴 **絕對不要說「bmv2 有 bug」。** 這份查證原本的主張就是「bmv2 違反規格」，
**被第三方 client 的實測推翻了，上游回報已取消**。交換機的行為完全正確，
**問題在我們重用了寫死的 election id**。三個情境實測：真的不同 id → 正確拒絕；
**id 撞號 → 接受，而且表被清成 0**；順序上，原 primary 的 stream 還活著時 pipeline 推得進去。

**可能被問**：「這算安全問題嗎？」→ 形狀上是控制面沒有身分隔離，但我們是實驗室內網，威脅模型不同。
真正要修的是**別再用寫死的 election id**（那就是缺口 G3，估 15 行）。

# 第三段　需求來自外部的人（p7–p15）

## p7　一夜的流程
**開場**：「第二種外部需求是人的動機。先講我們一個晚上怎麼跑。」

**內容**：六個階段。先跑上一夜留下的回歸測試當暖身。接著兩個唯讀的 agent 讀程式碼猜哪裡壞，猜出六十幾條。這些猜測先在離線環境殺一輪，能否證的當場淘汰。剩下的才派角色上機。找到的東西開修單，修法要有測試先看過紅才算數。最後把缺陷修好前的原始紀錄凍起來變成一個永遠會失敗的測試，下一夜當暖身跑。

**兩個重點**：六個階段裡**只有一個碰到受測機器**，這是一夜能跑 11 個角色的原因。還有**那條回饋線才是本體**——一條發現不是以「修好」收尾，是以「它出事當下的證據被凍成一個判決」收尾。

底下那條是每個角色都要做的：上機前存基線、下機後還原、逐項比對，對不上那一輪就作廢。

## p8　角色是兩個假設的交叉
**開場**：「那角色是怎麼設計的？不是隨便想人物。」

**內容**：規格裡寫得很清楚——**bug 不住在功能裡，住在假設的交界**。作者寫每一行的時候心裡都有一組沒寫下來的假設，而那些假設彼此從來沒有被一起想過。所以一個好的角色，就是一組作者沒有一起想過的假設。

格子的直軸是四條：時間、規模、狀態、意圖。橫的是六個人格。格子裡的編號是那一夜實際派出的角色。最下面那列 R7 不排隊，它整夜並行、只讀不寫，專門看**沒有人在場的空檔**，因為狀態不一致都住在那裡。

底下那句：**派工只給動機，不給題目。** 不會說「請測試併發」，而是說「你是一個接手別人實驗室的人」。動機才會生出你想不到的動作順序。

**可能被問**：「怎麼知道角色夠不夠？」→ 規格裡有入場費：每派一個新角色，先講得出它踩的是哪兩個假設的交界，講不出來就不派。

## p9–p15　七種實驗方法
**開場一次就好**：「11 個角色收斂成七種方法，因為四個人格被重派過，方法相同只換設定。接下來七頁一種一頁。」

🔴 **共同的但書**：圖上那四個步驟**是事後整理的，不是派工時給的**。派工只寫動機。講成「我們給了它一份流程」會把這套方法講反。

| 頁 | 角色 | 一句話 |
|---|---|---|
| p9 | 接班人 | 接手別人留著的實驗室，照系統自己印的建議做，然後看它動到誰的狀態 |
| p10 | 接班人第二次 | 拿修好的工具，把同一組觀測原樣再量一次。**修法自己也要被角色測一次** |
| p11 | 重開循環 | 開開關關十幾輪不清乾淨，每輪取樣，故意重疊兩次 |
| p12 | 第二個操作者 | A 做一件長的事，B 在中間插手，改變兩者的間隔 |
| p13 | 流量壓力狂 | 固定速率灌規則，逐一讀回覆，比對交換機真正持有什麼 |
| p14 | 趕論文的研究生 | 把系統自己供的拓樸存下來，照趕時間的人會犯的錯去改，再載回去 |
| p15 | 照手冊做的人 | 只讀手冊、照字面打、記下每一處輸出跟文字不符，不看原始碼 |

**p10 值得多講一句**：這是「修法自己也要被測」的實例，而且那一輪當場抓到前一條修法弄壞了開機指令。

# 第四段　角色找到了什麼（p16–p20）

🔴🔴 **這一段開場第一句就要講層級，不講會被誤會：**

「接下來五條裡，**只有一條是繼承來的系統的缺陷，其他四條是我們自己寫的工具**。角色扮演打到哪裡，就找到哪裡的問題。」

## p16　機器空了，而分身不知道（我們的工具）
**內容**：現場 0 個交換機、0 個 mininet、沒有拓樸 session，而 kernel 還在對外供一張 14 節點的圖。兩個本該攔住的工具，一個說「我沒查」，一個說「乾淨，沒有但書」。

**要講的點**：兩個工具**都沒有說謊**。問題是沒有人分得出「我沒查」和「我查過是乾淨的」這兩句的差別。

## p17　同一個欄位，兩扇門相反的答案（🔴 這條是 baseline）
**內容**：一個研究生想要一張圖，把系統自己供的拓樸存下來改，把節點型別打成 2（他以為 2 等於 router）。走檔案那條路**全收，零診斷，直接進圖**。而**同一個欄位走 API 會回 400**。同一扇門也收下 −1、99，還有一個寬鬆寫法的位址讓兩台主機共用同一個位址、十扇門零警告。

**要講的點**：這不是少一個檢查。是**兩條路徑對同一件事有相反的嚴格度，而使用者走的是寬鬆那條**。

## p18　兩個人同時被告知實驗室是他的（我們的工具）
**內容**：同一毫秒兩個人搶，兩個都拿到，16 次裡 2 次。間隔拉到 50 毫秒以上就全部正確拒絕。原因是先讀後寫、中間沒有鎖。

🔴 **橫軸不是等比例的**，只有那四個點是量過的。50 毫秒是「測過的最小安全間隔」，不是量到的臨界值。

## p19　拆除標記沒有主人（我們的工具）
**內容**：兩個拆除重疊。A 寫下標記，B 覆蓋它，A 先結束就把標記刪掉——而 B 還在跑。標記消失之後新的開機指令就不被拒絕了，一路走到最後一步。**沒撞成災難只是差幾秒。**

🔴 圖上的時間點是示意，不要講成量過的時序。

## p20　取樣的那一秒決定了結論（我們的工具）
**內容**：同一條連結、同一種切法，在八秒的視窗裡取樣三次得到三個不同的結論。下面那格是另一半：從 4 台拉到 128 台，檢查工具看到的東西**一個字都沒變**，因為多出來的 248 條邊全是面向主機的，全被排除。

**要講的點**：修法是對的，**不穩定的是量測窗口本身**。

# 第五段　我們修好的 baseline 缺陷（p21–p34）

**開場**：「剛才那段是工具。接下來這一段全部是繼承來的系統本身的缺陷。」

## p21　一個旗標兩個意思（Q12）
**內容**：`is_up` 這個欄位，電源 API 寫它的時候意思是「我命令它關了」，而每秒探測的那個 worker 寫它的時候意思是「它有回應」。一個位元分不出「牆上開關關了」跟「燈泡燒了」。

後果三條：命令關機後 0.3 到 1.5 秒被快取寫回 true，撐 8 到 13 秒；兩台一樣死透的交換機，被命令關的報 OFF、自己掛的報 ON；而「有沒有不該掛的東西掛了」這個檢查兩邊讀同一個位元，**結構上永遠不會響**。

**裁決**：拆成 admin_state 和 reachable 兩個欄位。🔴 **這是整輪唯一的 breaking change**，回應的形狀變了。

## p22　遙測越忙越說謊（#53）
**內容**：五個負載階梯。前三階一個都沒掉。到 15 萬每秒掉 0.34%，到 65 萬每秒掉 72.5%。**而每一階，每個端點都回 success。** 當時有四個丟棄計數器，沒有任何 API 讀得到。

修好之後，回應直接帶狀態、丟包率、**還有分子跟分母**，讀的人可以自己重算、不同意我們的門檻也不用再打一次 API。而且碼裡刻意不讓它四捨五入成 ok：低於門檻的丟包仍然是丟包。

🔴 **五個階梯不是等距的**，圖上等寬排列是示意。

## p23　你關掉它，輪詢把它開回來（#46）
**內容**：命令關機之後 3.08 秒，30 秒一輪的拓樸輪詢把那個旗標寫回 true。九次裡兩次。麻煩的是電源指令是唯一救得回來的路，而它讀的正是輪詢剛蓋掉的那個旗標。

## p24　一台交換機死了，幾乎沒東西跟著死（F-14）
**內容**：四個問題只有第一個誠實回答。交換機之間的邊被標 down 了，但它面向主機的邊還是 up，主機本身還是 up，而死掉的鏈路下一輪輪詢又被主機表憑 IP 復活。

## p25　刪除說沒了，group 還在（#1）
**內容**：kernel 送刪除的時候帶了 buckets，OVS 依規格拒絕，Ryu 不回錯誤，kernel 就回 200「已刪除」。讀回來 group 還在交換機上，而那個編號**永遠不能再用**。修法：只有交換機給出決定性的「是」，才准說已刪除。

## p26　流表早 13 秒就有那一列（#2）
**內容**：裝一條規則之後 0.257 秒，流表就顯示那一列——那是快取。交換機**13.4 秒**才真的有。中間那十三秒，分身是拿一個佇列當成網路在回答。

🔴 **時間軸非等比例**。

## p27　272 條邊剛好對（F-8）
**開場**：「這一頁我想講的不是錯的那 16 條，是對的那 272 條。」

**內容**：每條邊回報的容量都是 1 Gbit/s，那是欄位的初始值，一輩子沒被覆蓋過。宣告容量其實有從拓樸檔讀進來，但被寫給了**旁邊那個欄位**，漏掉了真正回報的那一個。

288 條邊裡 272 條讀到正確的值——**而理由是初始值剛好等於它們宣告的值**。只有 16 條宣告 10 G，每條少報 9 G。**而回應裡沒有任何欄位能讓人分辨那 16 條和那 272 條。**

🔴 那 16 條的 10 G 是**宣告**不是量到的，該拓樸算術上到不了 10 G（每台接取交換機只有兩條 1 G 上行，上限約 2 Gbit/s）。所以修法必須在 API 上把宣告和量測分開。

🔴🔴 **這一頁最容易被問倒的地方（09-16 查證後補）**：

**問**：「那 16 條上面的流量不是可以超過 1 G 嗎？那不就會算出 100% 以上的使用率？」

**答：不會，而且原因正是這條缺陷的範圍。** 這個欄位只在**從來沒有被取樣到流量**的邊上停在初始值。
一旦那條邊有過流量，它就會離開哨兵、拿到一個真的值。所以**會跑超過 1 G 的邊，恰好就是 F-8 碰不到的邊**。

🔑 **而這才是最該講的一句**：另一條缺陷（F-9）的量化地板讓「幾乎沒有流量」也會產生一個非零讀值，
於是連一點點流量都足以讓欄位離開哨兵。**兩條合起來看，永遠停在 1 G 的正好是最安靜、最沒有人在看的那些邊。**

⚠️ **兩個不要講過頭的地方**：
1. **夾制用的不是這個欄位**。使用率的上限夾制讀的是模型宣告值（那個是對的 10 G），
   所以不會因為 F-8 出現超過 100% 的讀數。
2. **已知的消費端不讀這個欄位**：平均鏈路使用率走的是另一組欄位；
   **Energy-App 的關機決策讀的是群組平均使用率，也不經過它**。
   ⇒ **不要說「這條害容量規劃做錯決策」**，那條因果鏈在 F-17 已經被推翻過一次。
   能講的是：**一個對外宣稱容量的欄位，在最安靜的邊上永遠是錯的，而沒有欄位說得出哪些是錯的。**

## p28　會說出自己算什麼的計數器（A-7）
**內容**：這一頁講修法怎麼做的。修法有兩半。第一半是公布「派送器還在不在跑」，這樣「在跑而且零丟棄」（健康）就能跟「沒在跑而且零丟棄」（配送早就結束了而沒人發現）分開。第二半是**公布分母**：明講它算的是哪四條路徑，並且直說不含開機期的程式化、不含 intent translator。

**最值得講的是被拒絕的那個選項**：他們本來可以替開機期的安裝加兩個計數器，但那種計數器結構上永遠會是 0。理由寫在設計文件裡——**一個永遠不會動的計數器比沒有計數器更糟。**

## p29　拓樸檔的 11 扇門
**內容**：這一頁是整份檔案的總結。11 種寫錯的方式，修法前**全部靜默收下**，現在全部拒絕。

**要講的那句在底下**：同一個值走 API 會被拒絕，走檔案會被收下。修法是把整份檔案在**第一個節點進圖之前**就驗完。

# 附錄　p3 那 16 個維度，逐個白話解釋

每一條都綁「哪支題目要它、要它幹嘛」，被問的時候照這個講。

## 交換機內建的資源（六個）

**`pre_multicast`　建群播群組**
交換機裡有一塊專門負責**把一個封包複製成多份**的硬體，叫封包複製引擎。
🔑 **P4 程式自己不能複製封包**，它只能在封包上寫一個數字：「這包屬於群組 1」。
至於群組 1 到底要複製幾份、送去哪幾個埠，**要控制器事先去那塊硬體裡建好一張對照表**。
`multicast` 那支：P4 程式只做一件事，把群組編號設成 1；控制面要建「群組 1 ＝ 埠 1、2、3」。
**沒有這個能力整支零分**——P4 那邊只寫了一個編號，而沒有人定義那個編號代表什麼。

**`pre_clone`　建複製 session**
同一塊硬體的另一個功能：**把封包複製一份送去別的地方，原本那份照走**。用途是鏡射或上送控制器。
一樣要事先建好：「session 57 ＝ 複製到 CPU 埠」，還可以指定只截前面幾個位元組。
`flowcache` 用它：查表沒中的封包複製一份給控制器看，控制器再決定要插什麼規則。

**`counters`　計數器**
交換機裡的計數器，記「這條規則命中了幾個封包、幾個位元組」，控制器可以去讀。2 支用到。

**`meters`　計量器**
比計數器多一層：它**會判斷**這股流量有沒有超速，超了就把封包標成紅黃綠，用來做限速。
**13 支一支都沒用** ⇒ 我們做不到，但那不是缺口。

**`registers`　暫存器**
交換機裡一小塊**P4 程式可以讀寫、而且跨封包保留**的記憶體。封包 A 寫進去，封包 B 讀得到。
`firewall` 用兩個當 bloom filter，記「這條連線是不是內部先發起的」；
`link_monitor` 用它記每個埠累積了多少位元組、上次是什麼時候。
🔑 **這兩支只在資料面用，控制面從來不讀** ⇒ 只要「能載入它的 P4 程式」成立就自動有了，
**我們的控制面讀不到暫存器，不構成缺口。**

**`digest`　摘要訊息**
交換機主動把一小筆資訊推給控制器的機制，比整包上送省。**13 支都沒用。**

## 封包長什麼樣（四個）

**`packet_io`　封包上送與下送**
讓封包在資料面和控制器之間走。上送＝交換機把封包丟給控制器看；下送＝控制器叫交換機送出某個封包。
兩個前提：封包前面要加一個**特別的標頭**說明它從哪個埠來；
還有**開機時要指定哪個埠是 CPU 埠**，那是交換機的啟動參數，跑時改不了。
`flowcache` 用它。🔴 **我們的缺口 G1 就在這**：我們解那個標頭時欄位編號是**寫死的 1 到 5**，
換一支 P4 程式編號就對不上，**遙測靜默歸零**。

**`custom_headers`　自訂標頭**
一般封包是乙太＋IP＋TCP。P4 的重點之一是**你可以自己定義新的標頭格式**，
用一個自訂的乙太型別標示它。這批題目裡有六種形狀：
tunnel 用 `0x1212`；calc 用 `0x1234` 做一個計算機協定；source_routing 用 `0x1234` 加**一疊下一跳**；
link_monitor 用 `0x812` 加**兩疊資料**；mri 塞進 **IPv4 的 option 欄位**（所以 IP 標頭會變長）；
flowcache 用控制器標頭。
**「一疊」的意思**是同一種標頭連續好幾個，每跳推一個進去。mri 就是每台交換機把自己的編號
和佇列深度推一個進去，收端拆開就知道封包走了哪條路。
🔴 **我們的缺口 G6 在這**：觀測面只認 IPv4，不是 `0x0800` 的整包丟掉 ⇒
**這六支「轉得動，但分身完全看不見」。**

**`queue_metadata`　佇列資訊**
封包在交換機裡排隊時，交換機會告訴 P4 程式：**你排進去的時候前面有多少**、
**你出來的時候前面還有多少**、排了多久。
`ecn` 用排進去的深度決定要不要標壅塞；`mri` 把出來的深度串進封包裡。
🔴 **這兩支對我們是「綠得很可疑」的風險**：如果那個深度永遠回 0，題目照樣會過，但什麼都沒測到。
**第三階段之前不可以把它們放進閘門。**

**`checksum`　校驗和**
IPv4 標頭有一個校驗碼。只要 P4 程式改了標頭裡任何欄位（例如 TTL 減一），**就必須重算**，
不然收端會把封包丟掉。10 支要重算，1 支要驗證。
🔑 **這是題目自己的 P4 程式做的，我們不用補**——能載入它的程式就自動有了。

## 為什麼這一整段可以這樣分

🔑 **上面「交換機內建資源」與「封包長什麼樣」這十個維度裡，大部分是題目自帶的 P4 程式自己滿足的。**
所以真缺口只剩三種：**要不要幫它裝程式（`pipeline_load`）、要不要幫它寫表（`tables`）、
還有那些「事先要在硬體裡建好」的東西（群播群組、複製 session）**。
這就是 p4 那張架構圖說「缺口全在控制面與觀測面」的意思。
